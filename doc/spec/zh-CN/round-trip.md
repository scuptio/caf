# 确定性往返:`project → .caf ⇄ .zip` —— 规范

> [English](../en/round-trip.md) | 简体中文

本文档是逐字节重建 `.caf` 构件的规范性契约:从项目源码重建(可复现构建),
以及从导出 ZIP 重建(重构)。它补充 `container-format.md`(字节布局),覆
盖**明文构件**;封存构件的重构作为未来工作规定在 §6。

术语:一条边是*字节确定*的,指相同输入重复执行得到相同字节;往返是*已验证
的*,指重构构件的根哈希被重新计算并比对,而不是被信任。

## 1. 为什么字节一致性是可达到的

格式的三个性质使字节一致的重构成为工程纪律问题,而不是运气:

- 段布局是段长度的纯函数:8 字节对齐的单次前向扫描
  (`container-format.md` §1)。清单从不存储偏移,因此没有自引用。
- 根哈希即内容身份。重算是密码学谕示器:重构正确**当且仅当**根哈希匹配
  ——正确性是被证明的,从不被假定。
- 明文构件没有随机输入:没有内容密钥,且 ed25519(RFC 8032)是确定性签名
  方案。

## 2. 规范构建(`project → .caf`)

合规构建是 `(项目文件, build.toml, 钉死的工具链)` 的纯函数。规则:

1. **排序枚举。** 载荷条目在每一层目录按文件名排序(深度优先);实现绝不
   可把文件系统 `readdir` 顺序泄漏进构件。WIT 源按 `build.toml` 的
   `interfaces` 列表顺序拼接。组件按 `build.toml` 声明顺序。
2. **不用墙上时钟。** 清单和任何段都不内嵌构建时间戳。构建元数据必须来自
   显式配置,绝不来自环境时钟。
3. **无随机性(明文)。** 明文构件没有随机输入;ed25519 签名是确定性的。
   封存构建必须设置 `[encrypt] key_seed`(收敛派生)才可复现;随机内容密
   钥会刻意使密文随机化。
4. **钉死工具链。** `source → .wasm` 编译不在 CAF 范围内:组件字节一致要
   求钉死编译器(`rust-toolchain.toml`、`cargo build --locked` 或容器镜
   像)。工具链未钉死时构建只是环境等价,而下述 `.caf ⇄ .zip` 边无论如何
   都保持字节确定。

## 3. 规范 ZIP 导出(`.caf → .zip`)

`caf-tool export` 写出的 ZIP 在每种模式下都是**内容确定**的:

1. 条目按固定顺序写入(`manifest.cbor`、`manifest.json`、`interfaces.cbor`
   及每个 WIT 源的 `interfaces/<name>`、按清单顺序的
   `components/NNNN.wasm`、按路径排序的 `payloads/<name>/` 树、
   `signatures.cbor`、`keybox.bin`、`export.json`)。
2. 时间戳为固定的 DOS 纪元默认值;权限固定(文件 `0o644`,目录 `0o755`)。
3. 压缩由调用方选择:`--compression deflate`(默认)或
   `--compression stored`。deflate 流在钉死 `flate2`/`Cargo.lock` 时是确定
   的,但可能随 zlib 实现不同而不同;`stored` 消除该变量,因此跨环境的 ZIP
   *字节*一致还要求 zip 写入器经 `Cargo.lock` 钉死。
4. `export.json` 携带 `export_version`(当前为 3)、原始 `root_hash`、
   `source_encrypted`、`format_version`、`signed` 以及组件名/路径映射。它
   是供验证和工具使用的元数据——绝不是排序依据。

## 4. 重构(`.zip → .caf`)

`caf-tool import` 重建字节一致的明文构件:

1. **权威来源。** 所有顺序来自保留的 `manifest.cbor`:组件顺序、载荷 DFS
   顺序、逐文件长度和 Merkle 哈希。ZIP 条目顺序和元数据绝不影响输出字节。
2. **条目验证。** 每个条目在使用前对照清单检查:接口的 SHA-256 和长度;每
   个组件的 SHA-256 和长度;每个载荷文件的长度和重算的 Merkle 根
   (`payload::verify_file`)。出现在 ZIP 中但不在清单中的载荷条目被拒绝。
3. **重组。** 在已验证的各段上重放规范布局(`container-format.md` §1):
   头部(`format_version` 来自清单,`FLAG_SIGNED` 当且仅当存在
   `signatures.cbor`)、清单、接口、重算的目录、组件、载荷文件、签名列表
   ——段间零填充。目录中载荷哈希是清单树哈希;签名条目的哈希为零。
4. **按序的验证关卡:** 逐条目哈希(第 2 步)→ 重算根哈希必须等于
   `export.json.root_hash` → 重构字节必须通过完整严格验证(`verify`),
   包括存在时的签名。任何失败都中止导入。
5. **原子发布。** 构件先写到目标旁的临时文件,fsync,所有关卡通过后才改
   名发布。已存在的输出需要 `--force`;失败时保留原文件。

结果与原始 `.caf` 字节一致;对签名构件,内嵌签名会对重构后的字节验签通
过,这是忠实重构的最强证明。

## 5. 验证矩阵(CI 关卡)

确定性是要测试的不变量,不是要断言的性质:

- 同一项目 `build × 2` → 字节一致。
- `build → export → import` → 字节一致且根哈希一致,覆盖语料包括未签名/签
  名、空文件与空目录、多块(> 1 MiB)载荷文件。
- `export × 2` → 两种压缩模式下 ZIP 字节一致。
- 模糊往返(对任意构件做 `export` → `import`)是未来工作。

## 6. 封存构件(未来工作)

明文导出会丢弃封存构件的密文,因此上述路径不适用。规定了两条重构路径但
**未实现**;`import` 拒绝封存导出并指向本节。

- **路径 A —— 原始导出。** 逐段原样导出(密文、填充、密钥盒、签名、目
  录)。重组不需要密钥,且签名按构造保持有效。此时 ZIP 是容器的展开视图,
  而不是明文读本。
- **路径 B —— 确定性重加密。** 用原始内容密钥从明文导出重建:块 nonce 是
  计数器,Pow2 填充配置是确定的,因此重加密精确复现原始密文;密钥盒原样
  接回(绝不重新包裹)。需要内容密钥——而导出本来就需要它。

两条路径都以与 §4 相同的谕示器收尾:重算根哈希,加上签名时的验签。
